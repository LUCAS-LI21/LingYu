# 实现 Skill

## 何时用

- 拿到一个已设计好的任务，开始写代码。
- 需要决定这次改动怎么切分提交。
- Code Review 时对照检查。

## 铁律

1. **一次提交只做一件事**，提交信息引用需求编号（如 `feat(FR-Q-07): 小区周边银行查询`）。
2. **先跑通，再优化**；但错误处理不能事后补。
3. **不许有裸奔的外部调用**：超时、重试、降级三件套。
4. **不写"以后再说"的 TODO 在主流程上**——要么现在做，要么建 issue。

## 步骤

### 1. 任务拆解（≤ 半天粒度）

- 输入：需求编号 + 设计契约。
- 输出：3-6 个可独立验证的小步骤，每步能编译、能跑。

### 2. 分支与提交

```
main
└── feat/FR-Q-07-nearby-bank   # 一个需求一条分支
```

- 提交前缀：`feat/fix/refactor/test/docs/chore/perf/ci`。
- 提交正文写「为什么」，不写「改了什么」（diff 已经说了）。

### 3. 后端实现要点（Spring Boot 场景）

- 分层：`controller`（参数校验、协议转换）→ `service`（业务编排、事务）→ `repository`（SQL）。
- 参数校验用 `@Valid` + 明确错误信息。
- 事务边界在 service；跨表写（POI + 版本 + 反馈状态）必须同事务。
- SQL 参数化，禁止字符串拼接；复杂查询走 XML/注解 SQL 并加注释。
- 外部调用统一走 `Client` 包装：超时 3s、重试 2 次、失败有降级返回。
- 幂等：抓取任务按 `source_id + source_ref` upsert；接口用幂等键。

### 4. 前端实现要点

- 数据请求集中在 `src/lib/http.ts`，统一错误提示。
- 列表/地图的三态（loading / empty / error）必须都实现。
- 大列表虚拟滚动或分页；地图标记按视口加载。
- 组件 props 全部有类型，禁止 `any` 穿透。

### 5. 数据库变更

- 所有 DDL 走迁移脚本（Flyway/Liquibase），命名 `V<n>__<desc>.sql`。
- 上线前评估：是否锁表、是否需要回填、回滚脚本是否可用。

### 6. 自测清单（提交前）

- [ ] 本地能启动，接口用 curl/Postman 跑通主流程
- [ ] 异常分支手工验证（无数据、超时、无权限）
- [ ] 日志里能看到关键上下文（traceId、任务 ID）
- [ ] 没有把密钥、内网地址写进代码

### 7. Code Review 清单

- [ ] 命名是否表达意图（`data`/`temp`/`util` 一律打回）
- [ ] 是否有重复逻辑可抽（第三次出现才抽）
- [ ] 事务范围是否过大（包住了外部调用？）
- [ ] 异常是否被吞掉（catch 后只打日志不处理）
- [ ] 是否有魔法数字（超时、分页大小、阈值）

## 产出物清单（DoD）

- [ ] 代码可编译、可运行、可测试
- [ ] 单测覆盖核心分支（见 `testing` Skill）
- [ ] 迁移脚本 + 回滚方案（若有 DDL）
- [ ] 更新接口文档/README
- [ ] 提交信息含需求编号

## 反模式

| 反模式             | 症状           | 修法                         |
| ------------------ | -------------- | ---------------------------- |
| 巨型提交           | 一次 80 个文件 | 拆成可回滚的小提交           |
| catch 后静默       | 出错无感知     | 记日志 + 上报 + 返回明确错误 |
| 事务里调外部 API   | 长事务锁表     | 外部调用移出事务             |
| 前端硬编码后端地址 | 换环境就挂     | 走环境变量                   |
| 只测 happy path    | 上线即炸       | 补 4 类异常用例              |
