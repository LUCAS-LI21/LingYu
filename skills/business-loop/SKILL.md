# 业务闭环 Skill

## 何时用

- 功能做完，但整个系统还是"静态展示"。
- 要回答评委："你的闭环体现在哪？"
- 需要设计运营看板或埋点。

## 铁律

1. **闭环 = 有触发器 + 有回流路径 + 有可见结果**，三者缺一不可。
2. **每条闭环必须能被一条自动化用例证明**，不能只写在 PPT 里。
3. **指标先于功能**：先定义"怎么算好"，再决定做什么。
4. **闭环要能自转**：没有人工干预时，系统也应持续变好（定时抓取、热点调度）。

## 闭环设计模板

对每条闭环填写：

```text
名称：纠错闭环
触发：用户提交反馈
处理：审核 / 自动生效
副作用：写版本、失效缓存、刷新展示
回流：状态回传用户；数据新鲜度提升
度量：处理时长、采纳率
证明：E2E 用例 feedback.spec.ts
```

## 本项目三条闭环（必须全部实现并演示）

| 链路   | 触发                 | 关键表                               | 可见结果                    |
| ------ | -------------------- | ------------------------------------ | --------------------------- |
| A 纠错 | 用户反馈错误         | `feedback` → `poi_version` → `poi_*` | 地图/列表立即更新，状态回流 |
| B 补采 | 查询为空点"请求补充" | `feedback` → `ingest_job`            | 抓取完成后新点位出现        |
| C 热点 | 查询日志聚合         | `query_log` → `hot_region` → 调度器  | 热点区更新频率提高          |

## 埋点设计

- 统一出口 `track(event, payload)`，字段固定：`event / path / ts / 业务字段`。
- 必埋事件：`page_view`、`search`、`filter_apply`、`poi_detail_open`、`feedback_submit`、`feedback_resolved`、`ingest_trigger`。
- 埋点要能回答业务问题：哪些区域查得多？哪些查询 0 结果（覆盖缺口）？

## 指标与看板（SLO 风格）

| 指标         | 定义                          | 目标     |
| ------------ | ----------------------------- | -------- |
| 数据新鲜度   | median(now - last_fetched_at) | ≤ 7 天   |
| 反馈闭环时长 | P90(处理完成 - 提交)          | ≤ 24h    |
| 热点覆盖率   | 热点区中 7 天内更新过的占比   | ≥ 80%    |
| 零结果率     | 查询 0 结果次数 / 总查询      | 下降趋势 |
| 任务成功率   | success / total jobs          | ≥ 95%    |

## 运营 SOP（写进文档，演示时讲）

1. 每日 03:00 定时抓取 → 看板检查成功率与新增条数。
2. 每天上午处理反馈队列（按风险与年龄排序）。
3. 每周看热点榜 → 调整抓取区域与频率。
4. 每月做一次数据质量盘点（重复率、可疑率）。

## 验证闭环是否"真闭"

- [ ] 断网/停抓取后，闭环是否还有数据进来？（没有 → 只靠人工）
- [ ] 反馈通过后，**不刷新页面**能否看到变化？（缓存策略）
- [ ] 反馈被驳回，用户能否看到原因？
- [ ] 热点调度有没有日志能证明"确实按热点抓了"？
- [ ] 三条链路的 E2E 是否都在 CI 里跑？

## 反模式

| 反模式       | 症状              | 修法                  |
| ------------ | ----------------- | --------------------- |
| 伪闭环       | 反馈只存表不生效  | 打通到主表 + 缓存失效 |
| 只有人工闭环 | 没有定时/热点调度 | 加调度器              |
| 指标不可算   | "用户体验提升"    | 换成可计算指标        |
| 埋点无消费方 | 记了没人看        | 上看板，定期复盘      |
