# 核查 / 防幻觉 Skill

## 何时用
- 要引用第三方项目、版本号、API 参数、标准条款。
- 要宣布"验证通过"、"性能达标"、"这个库支持 X"。
- 派子代理做调研或评审，需要判断其结论可信度。

## 三类断言，三种核查方式

| 断言类型 | 例子 | 核查方式 |
| --- | --- | --- |
| 事实型 | "这个仓库有 3 万 star" | 打开页面亲眼看到；否则标「未核实」 |
| 可执行型 | "构建通过" | 给出命令 + 退出码 + 关键输出 |
| 判断型 | "这个方案更好" | 列出对比维度 + 取舍理由，允许被反驳 |

## 铁律
1. **没有证据的结论必须标注**「未核实」，不许含糊其辞。
2. **URL 必须真实可打开**；模型记忆里的链接默认视为不可信。
3. **能跑的命令不要用"应该"**，跑完贴退出码。
4. **版本号要来自实际安装结果**（`package.json` / `mvn dependency:tree` / 命令行输出），不是"大概是最新版"。

## 子代理交叉审查流程

```text
1. 主代理产出结论/文档
2. 派 A 子代理：扮演"挑刺者"，只找漏洞、矛盾、未经验证的断言
3. 派 B 子代理（可选）：扮演"执行者"，按文档步骤实跑，报告失败点
4. 主代理逐条回应：接受 / 反驳（附证据）/ 标注未核实
5. 修订文档，记录修订原因
```

**评审提示词模板**：
```text
你是严格的评审者。只做三件事：
1) 找出文档中所有"不可验证的断言"，逐条列出并标出原文位置；
2) 指出技术方案中至少 3 个潜在失败模式；
3) 给出被你判定为"过度设计"的部分。
不要夸奖，不要复述原文，只输出问题清单。
```

## 常见幻觉形态（自查表）
- [ ] 编造仓库名/包名（`vue-map-pro` 之类听起来很像的）
- [ ] 版本号"最新是 5.x"（实际已到 8）
- [ ] API 参数名记错（`pageSize` vs `size`）
- [ ] 把"文档里没写"当成"不支持"
- [ ] 声称"已验证"但没给出命令输出
- [ ] 把 A 项目的特性安到 B 项目上

## 交付前的最后三问
1. 这份文档里，哪些句子我**没有证据**？标出来了吗？
2. 如果有人照着做，会在哪一步失败？
3. 我把"我认为"和"我验证过"分开了吗？

## 产出物
- 核查记录：`docs/research/verification-log.md`（结论 / 来源 / 核验时间 / 状态）
- 评审意见：附在对应文档末尾的「评审记录」小节
