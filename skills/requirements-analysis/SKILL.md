# 需求分析 Skill

## 何时用
- 项目启动，只有一个「想法」或一份赛题描述。
- 需求发生变更，需要评估影响面。
- 有人问「这个功能到底怎么算做完」。

## 铁律
1. **不可测量 = 不算需求**。"界面友好""响应快"必须改成「P95 < 800ms」「3 步内可达」。
2. **每条需求有唯一编号**（FR-域-序号 / NFR-序号），后续设计、用例、提交信息都引用它。
3. **先划范围，再谈细节**。MVP 之外的一律写进「范围外」，否则必延期。
4. **闭环类需求要写「触发器」和「可见结果」**，不能只写"支持反馈"。

## 步骤

### 1. 背景与目标（30 分钟）
- 用 3 句话回答：谁、在什么场景下、遇到什么麻烦。
- 目标写成 3-5 条可度量项（G1..Gn），每条给出度量方式。

### 2. 干系人与角色
- 列表：角色 / 关注点 / 对需求的影响。
- 只要某个角色能改变需求，就必须列出（评委也算）。

### 3. 范围切分
- **范围内（MVP）**：不做就交不了差的。
- **范围外（演进）**：写清楚为什么现在不做。
- 数量控制：MVP 功能条目 ≤ 15 条，超出就砍。

### 4. 用例建模（只写 P0）
- 每个用例 5 段：前置条件 / 主流程 / 异常分支 / 后置条件 / 关联 FR。
- 异常分支必须包含：无数据、超时、无权限、并发冲突。
- 用例命名用「动词 + 宾语」，如「提交纠错反馈」。

### 5. 功能需求（FR）
- 分域编号：采集 / 清洗 / 存储 / 查询 / 反馈 / 权限 / 运营。
- 每条格式：**编号 | 需求描述 | 优先级(P0/P1/P2) | 验收标准**。
- 验收标准必须能写成一条测试用例（给条件、做操作、断言结果）。

### 6. 非功能需求（NFR）
- 六类必查：性能、可用性、安全、合规、可维护/可扩展、可观测。
- 性能写成百分位（P95/P99）+ 数据量级 + 测量方法。
- 合规要落到「技术实现方式」，不能只写"要合规"。

### 7. 业务闭环
- 画出「A → B → C → 回到 A」的回路，标出每个箭头的**触发器**。
- 每条回路给一个**可演示的脚本**（谁点哪里、看到什么）。
- 给出闭环度量指标（新鲜度、处理时长、覆盖率）。

### 8. 数据需求
- 实体清单 + 关键字段 + 质量规则 + 量级假设。
- 量级决定索引与分页策略，不能拍脑袋写"海量数据"。

### 9. 风险与待决问题
- 风险表：概率 × 影响 × 应对。
- 待决问题：给出选项 + 建议 + 影响面，**不要替用户拍板**。

## 产出物清单（DoD）
- [ ] SRS（含背景/范围/用例/FR/NFR/闭环/验收/里程碑/风险/待决）
- [ ] 数据字典草案（实体 + 字段 + 索引意图）
- [ ] 合规说明（来源分级 + 检查清单 + 红线）
- [ ] 验收矩阵：每条 P0 需求都能指到一个验证方式
- [ ] 演示脚本（≤10 分钟，可一次跑通）
- [ ] 待决问题清单（≤ 7 条，每条有建议）

## 反模式（看到就打回）
| 反模式 | 症状 | 修法 |
| --- | --- | --- |
| 需求是一句话愿景 | "做一个好用的系统" | 拆成用例 + 验收标准 |
| 只有正向流程 | 没有异常分支 | 补 4 类异常 |
| 闭环写成静态展示 | "展示数据给用户看" | 补触发器 + 回流路径 |
| 范围无边界 | MVP 列出 30 条 | 砍到 15 条以内 |
| 不可测的 NFR | "速度快" | 改成 P95 + 数据量级 |
