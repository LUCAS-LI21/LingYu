# 数据接入 Agent（设计草案）

> 目标：把"每来一个新数据源就要人写一个适配器"变成"Agent 按工作流自动完成接入与补全"。
> 状态：**设计草案，待评审**。实现见后续提交。

## 1. 为什么需要

现状：65 个银行品牌 + 政府数据集 + 用户反馈，每家页面结构不同（建行是 `WCCMainPlatV5` 网关、
招行是 SPA、工行 JS 渲染）。人工一家家写适配器，TOP 10 就要 1–2 周。

## 2. 两条"AI 适配"路线（重要区别）

| 路线              | 做法                                                  | 风险                                     | 结论            |
| ----------------- | ----------------------------------------------------- | ---------------------------------------- | --------------- |
| A. LLM 写抓取代码 | Agent 生成 Python/JS 脚本并执行                       | 代码执行不可控、页面对不上就崩、难审计   | ❌ 运行时禁用   |
| B. LLM 做字段抽取 | 抓取仍由固定代码完成，LLM 只把页面内容转成结构化 JSON | 输出需 Schema 校验，幻觉可用证据片段拦截 | ✅ **默认路线** |

**A 的变体（推荐作为第二阶段）**：Agent 生成"适配器配置"（URL 模板、选择器、字段映射），
**人工审核后落库为配置**，运行时不执行任何 LLM 生成的代码。既省人力又不失控。

## 3. 运行时工作流（MVP）

```text
触发（反馈/手动/定时）
   │
   ├─1 意图解析：要补哪个实体的哪些字段（JSON Schema 约束）
   │
   ├─2 选源：按白名单 + 字段优先级选（政府/官网 > OSM > 用户反馈）
   │
   ├─3 抓取：robots 预检 → 限速 1 req/s → 存原始 HTML/JSON 快照（可溯源）
   │
   ├─4 抽取：LLM 输出 {field, value, evidence, confidence}，必须过 Schema
   │
   ├─5 校验：坐标范围 / 地址格式 / 与已有实体一致性 / 交叉源比对
   │
   ├─6 落库 or 人审：置信度 ≥0.85 自动写入；0.6–0.85 进审核队列；<0.6 丢弃
   │
   └─7 记账：agent_run（输入、步骤、token 消耗、结果、耗时）
```

## 4. 关键护栏

| 护栏     | 规则                                                        |
| -------- | ----------------------------------------------------------- |
| 源白名单 | 只允许已核验 robots 的域名；未核验域名直接拒绝              |
| 预算     | 单次 run ≤ 5 个请求、≤ 60 秒、≤ 8000 token；超限中止        |
| 证据     | 每个字段必须带 `evidence`（原文片段 + 来源 URL + 抓取时间） |
| 幂等     | 同一 (entity, field, source) 24 小时内不重复跑              |
| 幻觉拦截 | 值必须能在 evidence 中找到子串；地址必须匹配行政区词典      |
| 人审兜底 | 低置信度、与既有值冲突、涉及坐标/名称的变更 → 审核队列      |

## 5. 合规边界（用户想法的关键澄清）

用户设想：「官方文档找不到，就先上高德找名字，再按名字全网找数据」。

**这里有个坑**：高德返回的**名字本身也是"服务数据"**，直接写进我们库里仍然属于"存储"，
违反服务协议 3.5 条——不管后续有没有再搜一遍。

可行做法（**线索中转，不留痕**）：

1. 高德只在"人工/实时查询"时用来**发现**实体存在（不落库）
2. 拿到名称后，去**独立来源**（银行官网 / 政府数据 / OSM / 企业公示）确认并取数
3. 入库时 `source` 记录的是**独立来源**，不是高德
4. 若独立来源查不到，则该字段保持空缺——**宁可缺，不留违规来源**

> 一句话：高德可以作为"搜索框"，不能作为"数据源"。

## 6. 与赛题对应

- 「数据抓取与更新」：多源、可扩展
- 「业务闭环」：反馈 → Agent 补全 → 审核 → 生效
- 「便于扩展新的数据源」：Agent 配置化接入
- 答辩价值：把"人工写适配器"变成"Agent 按工作流接入"，是明确的创新点

## 10. 模型与检索能力（2026-11-10 已核实）

来源：<https://api-docs.deepseek.com/zh-cn/quick_start/pricing>（HTTP 200）+ 真实调用。

| 项                     | 事实                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------- |
| 模型名                 | `deepseek-flash`，对应 **DeepSeek-V4.1-Flash-1017**（旧名 `deepseek-v4-flash` 仍可用） |
| 上下文 / 输出          | 1M / 最大 384K                                                                         |
| 能力                   | JSON Output ✅、Tool Calls ✅、思考模式（**默认开启**）                                |
| 价格（元/百万 tokens） | 输入缓存未命中：空闲 1 / 高峰 2；输出：空闲 4 / 高峰 8                                 |
| 并发                   | 2500                                                                                   |
| **Search / Fetch API** | **5 元 / 1000 次成功请求**（即 0.005 元/次），平台自带，无需第三方                     |

实测（真实调用）：一次「HTML → 结构化字段 + 证据」抽取耗时 **2.3 秒**、**469 tokens**，
按空闲价约 **0.0005 元/次**。

> **思考模式默认开启**，抽取类任务会额外消耗 reasoning tokens。实现时应显式关闭思考模式，
> 既省钱又快（本次 469 tokens 里有 202 是 reasoning）。

**关于"免费搜索 API"**：不必再找第三方。DeepSeek 自带 Search（0.005 元/次），
一次补全最多 2–3 次搜索，成本 < 0.02 元。第三方免费方案（DuckDuckGo HTML、自建 SearXNG）
要么不稳定、要么需自维护，性价比不如直接用平台自带。

## 11. 多 Agent 拓扑（用户设想 + 我的修正）

用户设想：总 Agent 调度 + 每步子 Agent 复核 + 管理员终审。**可行**，但要说清一件事：

> **多 Agent 复核不能消除幻觉**——同一模型自查容易"同错"。
> 真正拦住幻觉的是「证据可验证 + 规则校验 + 外部交叉源」，复核 Agent 只是第二道过滤。

因此拓扑设计为「**LLM 负责理解，代码负责判定**」：

```text
Orchestrator（总 Agent，规划/派单/汇总）
   ├─ Planner       解析缺口 → 任务单 {entity, fields[], candidateSources[]}
   ├─ Fetcher       固定代码：robots 预检 + 限速 + 快照存档（不用 LLM）
   ├─ Extractor     LLM：快照 → {值, evidence, confidence}
   ├─ Verifier      LLM（独立上下文，只看「值+证据」）：证据是否真的支持该值
   ├─ Critic        固定代码：坐标范围/地址词典/与既有值冲突/证据子串匹配
   ├─ Judge         LLM：综合三项给最终置信度与建议（自动 / 人审 / 丢弃）
   └─ AdminGate     现有后台审核（最终上线必须人工点）
```

**成本**：一次补全 ≈ 3 次 LLM 调用 × 500–1000 tokens ≈ **0.01 元以内**；延迟 ≈ 5–8 秒。
**为什么可控**：LLM 只做「读页面、写 JSON」，抓取与判定都是确定性代码；每一步都有 `agent_run` 记录。

**与赛题的对应**：这套拓扑本身就是"数据持续更新 + 用户参与 + 审核上线"的闭环实现，
比手写 65 个适配器更能体现"便于扩展新的数据源"。
