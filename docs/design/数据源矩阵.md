# 数据源矩阵：每个字段从哪来、能不能入库

> 回答两个问题：① 赛题要的字段分别由哪个源提供？② 哪些能存进本地库、哪些只能实时展示？
> 核验日期：2026-11-05。标注「未核实」的，请在启用前自行阅读该平台最新条款。

## 0. 一句话结论

**不能只靠 OSM**：它只能覆盖赛题 10 个字段中的 4 个（名称、坐标、部分地址、部分电话/营业时间），
且银行地址覆盖率仅 5.5%。正确做法是**多源分层**：能存的存（L1），只能看的实时取（L2），禁止的不碰（L3）。

## 2. 逐源分析

| 项     | 内容                                                                 |

**深圳平台服务条款原文（决定能不能入库的关键）**：

- 第四项(一)1：「用户有权免费获取开放平台所提供的数据资源，享有数据资源的**非排他使用权**。用户**不得有偿或无偿转让**在开放平台中获取的任何数据资源。」
- 第四项(二)2：「未经开放平台所有者书面授权，任何人**不得建立开放平台的镜像**（包括全部或局部镜像）。」
- 同项：「用户须在使用开放平台数据资源所产生的成果中**注明数据资源来源**为"深圳市政府数据开放平台"。」

> 结论：**存储 + 二次使用可以（须署名），再分发/转让/镜像不可以。**
> 这正好允许我们建库、查询、展示，但不允许把数据打包给别人。

#### 接口 vs 下载（2026-11-10 实测）

平台在页面上提示「数据过多，建议直接调用接口，下载只给前 1 万条」。实测结论：

| 项        | 结果                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 接口地址  | `https://opendata.sz.gov.cn/{api_context}?page=1&rows=10&appKey=xxx`，其中 `api_context` 由 `/data/api/getApiDocument` 返回（如 `api/1514671018/1/service.xhtml`） |
| 费用      | **不收费**。依据服务条款「用户有权免费获取开放平台所提供的数据资源，享有数据资源的非排他使用权」；接口与下载是同一份数据                                           |
| 鉴权      | 必须用自己账号在开发者中心申请的 `appKey`。文档里的示例 key（`89d07f08…`）已失效，调用返回 `10001 未经许可的证书`                                                  |
| 缺 key    | 返回 `10009 appKey不能为空`                                                                                                                                        |
| 配额/频次 | ⚠️ **未核实**，脚本按 1 请求/秒 保守执行                                                                                                                           |

**⚠️ 字段现实（比预期少）**：接口文档里的字段清单显示，这两个"最相关"的数据集都**没有坐标、没有地址**：

| 数据集                 | 业务字段                                                                                     | 缺什么                   |
| ---------------------- | -------------------------------------------------------------------------------------------- | ------------------------ |
| 小区物业项目查询       | `PROJECT_NAME`（项目名）、`DIST_NAME`（区）、`PROJECT_TYPE`、`STAFF_NAME`（物业公司）、`SEQ` | 无地址、无坐标、无物业费 |
| 二手住房成交参考价格表 | `PRJ_NAME`/`PRJ_NAME2`、`ZONE`、`ZDJ`（指导价）、`JDNAME`（街道）                            | 无坐标、无地址           |

→ 所以这两个数据集**不能新增 POI**，只能「按名称匹配已有小区后补价格/物业公司」。
为此导入器增加了 `enrich` 模式：只按名称（可带区）匹配，匹配不到或同名多条一律跳过，绝不新建无坐标记录。

### 2.10 已接入：政府数据导入管线

平台下载需要登录，因此**不做自动下载**，改为「人工下载 → 脚本导入」：

```bash
# 1. 登录深圳开放数据平台，下载「小区物业项目查询」xlsx，另存为 CSV
# 2. 按列映射导入（自动去重 + 写来源 + 写版本）
node scripts/import-opendata.mjs --file 小区物业.csv --type community \
     --map "小区名称=name,地址=address,经度=lng,纬度=lat"
```

后端接口：`POST /api/v1/admin/import`（需登录）。

- 去重：有 id 用 id；无 id 时按「同名 + 165m 内」判定同一实体
- 补全：只覆盖有值字段，不用空值冲掉已有数据
- 溯源：写入 `source` / `license`，变更写 `poi_version`（operator=`import:来源`）

**实测**：4 行样本 → 新增 1 / 更新 1 / 跳过 2（缺名称、坐标越界），版本记录正确。

## 3. 为什么多源之后项目才有优势

| 维度       | 单源（只有 OSM）         | 多源分层                                                       |
| ---------- | ------------------------ | -------------------------------------------------------------- |
| 字段覆盖   | 10 个字段里只能覆盖 4 个 | 坐标/名称走 OSM，地址/电话/营业时间走银行官网，均价走政府+反馈 |
| 数据可信度 | 无法交叉校验             | 同一实体多源比对，一致则高置信，冲突则标"待核实"               |
| 抗故障     | Overpass 一挂就停更      | 单源失败只降级该源，其余照常                                   |
| 实时性     | 受限于 OSM 编辑频率      | 用户点开即查高德/百度，体验新                                  |
| 扩展性     | 加源要改核心代码         | 适配器模式：新增源只实现接口                                   |

**一句话**：赛题考的不是"你能抓多少"，而是"**你能把多少源的数据合规地组织成一个持续更新的系统**"。

## 6. 落地顺序（拿到 Key 后）

1. **P0**：高德 Key → 详情页「查实时地址 / 查实时周边」可用（代码已就绪，缺 Key）
2. **P1**：银行官网适配器 → 补地址/营业时间/电话进 L1 库（这是对数据质量提升最大的一步）
3. **P1**：百度 AK → 与高德交叉校验，冲突标待核实
4. **P2**：政府开放数据 → 行政区划 + 人口 + 小区名录
5. **P2**：天地图底图 → 替换 OSM 瓦片
6. **长期**：房产均价只能靠「政府参考价 + 用户反馈」，不碰 robots 禁止站点

## 7. 合规红线（再次确认）

- L2 数据**绝不写库**，响应头 `no-store`，日志不记响应体
- L3 站点（链家/贝壳）不访问，白名单直接拒绝
- 每源限速 ≤ 1 QPS，带自定义 UA 与联系方式
- 抓取前校验 `robots.txt` 并缓存结果
- 页面标注来源与许可，提供免责声明
