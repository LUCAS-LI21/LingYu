# ADR-0001：实时数据层（L2）与本地库（L1）分离

- 状态：**提议（待确认）**
- 日期：2026-11-05
- 决策者：项目负责人 + 开发
- 相关需求：FR-D-17、FR-D-18、FR-Q-01、FR-Q-07、§7.4

## 背景

高德开放平台服务协议 3.5 条明确：只能"对相关服务数据的结果进行展示"，**不得直接存储、缓存或技术手段抓取、使用本服务内部数据**（已核验条款原文，2026-11-05）。

赛题既要求"从地图服务获取数据"，又要求"数据抓取不能违法"，因此需要一种既能用上地图服务、又不违反 3.5 的架构。

## 决策

采用**双层数据架构**：

| 层            | 数据来源                                               | 是否入库          | 用途                                   | 延迟目标    |
| ------------- | ------------------------------------------------------ | ----------------- | -------------------------------------- | ----------- |
| **L1 本地库** | OSM/Overpass（ODbL）、政府开放数据、种子数据、用户反馈 | ✅ 入库           | 地图总览、列表筛选、统计图表、周边关联 | P95 < 300ms |
| **L2 实时层** | 高德 Web 服务 API（`/v3/place/around`）                | ❌ 不落库、不缓存 | 用户显式触发的"查实时"补充             | P95 < 800ms |

### L2 的硬约束（必须实现）

1. **只在用户显式触发时调用**：点击"查实时"按钮，或本地库在该视口结果 < 5 条时自动提示（由用户点确认），不做后台预取。
2. **不写任何表**：不写 `poi_bank`/`poi_community`，也不写 `ingest_log` 的响应体；只记一次"调用发生"的计数。
3. **不缓存**：响应头 `Cache-Control: no-store`，前端只存内存变量，**禁止写 localStorage / sessionStorage / IndexedDB**。
4. **不记原文**：日志只记 `grid_id`、结果条数、耗时，不记名称/地址/坐标。
5. **限流**：每 IP 30 次/分钟；全局 QPS ≤ 3；触发熔断后自动降级为"仅本地库"。
6. **来源标注**：结果卡片固定显示"实时数据来自高德，未存储"。

### 反哺闭环（关键设计）

L2 每次调用后只落一条**聚合信号**到 `coverage_gap`（新增，非 POI 数据）：

```
coverage_gap(grid_id, local_count, live_count, queried_at)
```

- `local_count` = 本地库在该网格的条数
- `live_count` = 实时层返回的条数（**只存数字，不存内容**）
- 用途：`local_count` 低而 `live_count` 高 → 说明该网格是数据缺口 → 驱动 L1 数据源补采

这样实时层不但不违规，还成了"查询驱动采集"的信号源，直接服务闭环链路 C。

### 为什么不做"Agent 实时取数"

用户曾提议"用 Agent 做实时爬取会更快"，经评估**否决**，理由：

1. LLM 推理需 1–3s，而高德 API 本身 150–300ms（未实测），加 Agent 只会更慢。
2. 网络往返时间不会因中间加一个大模型而缩短。
3. 真正的加速手段是：多类型合并请求（`types=a|b|c`）、并发 2–3 路、前端 debounce、只查视口中心 1km。
4. Agent 的正当位置在**异步侧**：自然语言查询解析、离线数据清洗、反馈工单分类。

## 备选方案

| 方案                                    | 否决/采纳理由                                                                                |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| A. 前端直连高德 JS API                  | 少一跳、更快；但 Key 暴露在前端（靠域名白名单保护），且难做统一限流与审计 → 作为二期可选优化 |
| B. 后端代理 + 不落库（**本 ADR 采用**） | Key 不暴露、限流与审计集中、无状态；代价是多一跳约 50–100ms                                  |
| C. 高德 API 采集入库                    | **否决**：违反协议 3.5                                                                       |
| D. Agent 编排实时取数                   | **否决**：增加 1–3s 延迟，不解决网络往返                                                     |

## 后果

**正面**

- 合规：L2 严格无状态，符合 3.5。
- 体验：本地库毫秒级响应，实时层只做增量补充。
- 闭环：`coverage_gap` 让实时查询反哺 L1 补采。

**负面 / 代价**

- 需要高德 Key；无 Key 时 L2 整体降级（功能仍可用）。
- 多一层代理与限流实现（约 1–2 人日）。
- L2 结果与 L1 结果可能重复，前端需按"名称+100m"去重展示（不落库）。

**未验证项**

- 高德 around 接口的实际延迟与单页上限（需 Key 实测）。
- 高德是否允许经自有服务器中转后返回给自建前端（条款未明说，建议启用前咨询工单）。
