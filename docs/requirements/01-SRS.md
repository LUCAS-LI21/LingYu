### 0.3 术语

| --- | --- |
| POI | Point of Interest，兴趣点。本系统特指**银行网点**与**小区**两类 |
| 数据源 | 提供 POI 数据的渠道，如高德开放平台、银行官网、公开房产列表页 |

## 1. 项目背景与目标

### 1.1 背景
用户在办理金融业务、选择居住地时，需要综合了解周边银行网点与小区信息。这些数据分散在地图服务、房产网站、银行官网，查询方式单一、无法关联分析。赛题要求做一个能自动采集、多维度查询、并形成**数据持续更新与用户参与优化**闭环的系统。

### 1.2 业务痛点（需求的来源）
1. **数据分散**：银行网点在高德/银行官网，小区在房产网站，用户需在 3-5 个 App 间跳转。
2. **无法关联**："这个小区 1 公里内有哪些 ATM" 这类问题，现有工具答不了。
3. **数据会腐坏**：网点搬迁、关闭，小区均价变化，静态数据三个月就失真。
4. **缺少反馈通道**：用户发现错误只能忍，平台无从改进。

### 1.3 系统目标（可度量）
| 编号 | 目标 | 度量方式 |
| --- | --- | --- |
| G1 | 一个入口看全周边 | 单次查询可在 1 个页面内同时获得银行 + 小区 + 统计信息 |
| G2 | 数据能自动保鲜 | 支持定时任务；单条 POI 的平均数据新鲜度 ≤ 7 天（可配置） |
| G3 | 用户能参与纠错 | 反馈提交 → 生效的全链路可追踪，闭环时长可统计 |
| G4 | 查询反哺采集 | 热点区域的重抓优先级高于冷区（可观测调度日志） |
| G5 | 合规可交付 | 全部采集行为有来源记录、有速率限制、有 robots 校验记录 |

## 2. 范围

### 2.1 MVP 范围内（必须交付）
1. 两类 POI：银行网点、小区。
2. 一个主数据源：高德开放平台 Web 服务 API（POI 搜索），可扩展到第二个源。
3. 单城市（默认杭州，可配置切换）。
4. 地图视图（标注、缩放平移、点击弹窗、图层切换、框选查询）。
5. 列表视图（区域/类型/价格区间/建成年代筛选，排序，分页）。
6. 关联查询：小区周边 N 公里银行。
7. 统计：区域银行密度、小区价格分布。
8. 反馈：提交纠错/新增 → 审核 → 生效 → 记录版本。
9. 抓取：手动触发 + 定时调度 + 增量去重 + 执行日志。
10. 部署：`docker compose up` 一键起（MySQL + 后端 + 前端）。

### 2.2 MVP 范围外（本期不做，留演进）
- 多城市并行、跨城对比。
- 机器学习去重/地址匹配。
- 移动端 App / 小程序。
- 实时爬虫（秒级）、反爬对抗。
- 用户体系对外开放注册（本期仅内置账号）。
- 支付、会员等商业化能力。

| 角色 | 说明 | 主要权限 |
| --- | --- | --- |
| 访客 Visitor | 未登录用户 | 浏览地图、列表、统计；提交反馈受限（需留联系方式） |

### 4.2 关键用例详细描述（P0）

**UC-05 小区周边银行关联查询**
- 前置：系统中存在该小区，且其周边数据已采集。
- 主流程：用户在地图点击小区 → 详情卡片 → 选择半径（500m/1km/3km）→ 系统按球面距离筛选银行网点 → 地图高亮 + 列表展示距离与类型（网点/ATM）→ 可继续下钻详情。
- 异常：周边无数据 → 提示"该区域数据覆盖不足"，并提供"请求补充采集"按钮（该按钮即闭环入口，产生一条反馈并可能触发抓取任务）。
- 后置：本次查询写入 `query_log`，参与热点统计。

**UC-08 提交纠错 / 新增反馈**
- 前置：用户看到某条 POI 信息有误或缺失。
- 主流程：选择反馈类型（信息错误 / 已关闭 / 新增点位）→ 填写字段与证据（可选上传截图 URL）→ 提交 → 系统按规则分流：
  - 低风险字段（电话、营业时间、均价）→ 直接写入"待复核"版本，先展示为"用户提供"标注；
  - 高风险（坐标、名称、关闭状态）→ 进入待审核队列；
  - "新增点位" → 生成定向抓取任务（以提交点为中心，半径 1km）。
- 后置：反馈状态可查询；状态变更通知提交人。

**UC-09 审核反馈并生效**
- 主流程：运营打开待审队列 → 查看差异（旧值 / 新值 / 证据）→ 通过/驳回 → 通过则写 POI 新版本、更新主表、刷新缓存 → 地图与列表立即可见 → 反馈状态置为已采纳，记录操作人。
- 异常：审核时发现数据源本身已变 → 直接触发该点重抓后再判定。

## 5. 功能需求

> 编号规则：`FR-<域>-<序号>`。每条需求必须可测试；优先级 P0（MVP 必须）/ P1（应做）/ P2（可做）。

### 5.1 数据采集域（FR-D）

| 编号 | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-D-01 | 支持配置多个数据源（名称、类型、接入方式、速率上限、启用开关），数据源可增删改查 | P0 | 后台新增一个数据源后，抓取任务可选用它 |
| FR-D-02 | 通过高德开放平台 Web 服务 API 按"城市 + 关键字 + 类型"分页采集银行网点与小区 | P0 | 给定城市与关键字，可采集到 ≥50 条并落库 |
| FR-D-03 | 支持手动触发抓取（指定数据源、城市/区域、POI 类型、页数上限） | P0 | 后台点击触发后 5s 内出现任务记录，状态从 pending→running→success/failed |
| FR-D-04 | 支持定时抓取（cron 表达式可配置，默认每日 03:00） | P0 | 到达设定时间自动产生任务并执行成功 |
| FR-D-05 | 增量更新：以数据源侧唯一标识去重，已存在则更新变更字段，不存在则新增 | P0 | 同一批次重复执行两次，记录总数不增加 |
| FR-D-06 | 去重：除 `source_ref` 外，按"名称相似度 + 坐标距离 < 100m"做二次判重，命中则合并并记冲突 | P1 | 构造两条同名同位置数据，库中只保留一条并生成合并日志 |
| FR-D-07 | 抓取限流：单数据源 QPS/并发可配置，默认 ≤ 1 请求/秒；连续失败自动退避 | P0 | 压测 10 分钟无超出配置的请求间隔，日志可查每次请求耗时 |
| FR-D-08 | 合规校验：抓取前检查目标是否在允许清单（官方 API 域名 / robots 允许路径），不满足则拒绝执行并记录原因 | P0 | 配置一个未授权域名，触发任务应被拒绝且日志给出原因 |
| FR-D-09 | 任务日志：记录任务参数、开始/结束时间、成功/失败条数、错误摘要、数据源与触发方式（manual/schedule/feedback） | P0 | 任务详情页可看到上述全部字段 |
| FR-D-10 | 支持"反馈驱动的定向抓取"：以坐标 + 半径生成抓取范围 | P1 | 提交"新增点位"反馈后，自动生成一条 scope=radius 的任务 |
| FR-D-11 | 抓取结果保留原始响应（raw payload）供追溯，可配置保留期 | P1 | 数据库中可查某条 POI 的原始 JSON |

### 5.2 数据清洗域（FR-C）

| 编号 | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-C-01 | 缺失值处理：必填字段（名称、坐标）缺失的数据进入"隔离区"不入主表，并记录原因 | P0 | 构造缺坐标数据，主表无该记录，隔离区可查 |
| FR-C-02 | 地址标准化：统一"省市区街道"层级，去除括号注释与重复分隔符 | P0 | 对同一地址的 3 种写法，标准化结果一致 |
| FR-C-03 | 坐标系归一：GCJ-02 / BD-09 / WGS-84 统一转换为 GCJ-02 存储，同时保留原始坐标 | P0 | 已知坐标点的转换误差 < 50m（抽样验证） |
| FR-C-04 | 字段归一：银行品牌（工行/ICBC → 中国工商银行）、网点类型（营业网点/ATM/自助银行）、小区建成年代（"2005年"/"2005"→2005） | P0 | 归一规则表可维护，命中率统计可见 |
| FR-C-05 | 异常值剔除：坐标落在城市行政范围外、均价为负或 > 50 万/㎡、建成年份 > 当前年 的数据标记为可疑 | P1 | 可疑数据不出现在默认查询结果中，可在质量报表查看 |
| FR-C-06 | 清洗规则可配置且可回放：对历史数据执行同一规则产生新版本 | P2 | 修改规则后重跑，生成变更记录 |

### 5.3 数据存储与管理域（FR-S）

| 编号 | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-S-01 | 结构化存储：银行、小区、地理信息、数据源、任务、反馈、用户、审计分表设计 | P0 | 表结构与第 7 节一致，含必要索引 |
| FR-S-02 | 版本管理：每次字段变更写入版本表（变更前后快照、来源、操作人、时间） | P0 | 修改一条 POI 后，版本表新增一条记录且可还原 |
| FR-S-03 | 来源追溯：每条 POI 记录 `source_id` + `source_ref` + `last_fetched_at` | P0 | 详情页可显示"数据来源：高德开放平台，更新于 X" |
| FR-S-04 | 软删除与状态机：POI 有 active / closed / pending_verify / rejected 状态，关闭不物理删除 | P0 | 标记关闭后默认查询不返回，但历史与反馈仍可追溯 |
| FR-S-05 | 空间查询支持：支持按矩形范围与球面半径检索 | P0 | 10 万级数据下，1km 半径查询 P95 < 300ms |
| FR-S-06 | 数据质量报表：按数据源统计缺失率、重复率、可疑率、新鲜度 | P1 | 报表可按周查看 |

## 6. 业务闭环设计（核心章节）

### 6.1 闭环总图

```text
        ┌──────────────────────────────────────────────────────┐
        │                                                      │
        ▼                                                      │
 [1] 数据采集 ──► [2] 清洗入库 ──► [3] 查询展示 ──► [4] 用户反馈
   ▲   (定时/手动/反馈触发)   (版本+追溯)     (地图/列表/统计)    (纠错/新增)
   │                 │                                  │
   │                 ▼                                  ▼
   │          [6] 调度优化 ◄──── [5] 审核与生效 ◄──── 反馈队列
   │           (热点驱动)          (通过/驳回/重抓)
   └─────────────────┴──────────────────────────────────┘
```

### 6.2 三条闭环链路（必须全部可演示）

**链路 A：纠错闭环（用户 → 数据）**
用户发现"招商银行某支行已关闭" → 提交反馈（类型=已关闭，附证据）→ 进入审核队列 → 运营通过 → POI 状态置 `closed`，写版本记录 → 地图标记变灰、列表默认隐藏、详情显示"已关闭（用户反馈，2026-11-05）" → 反馈状态回流给用户。

**链路 B：补采闭环（缺口 → 抓取）**
用户在某小区选择"周边 1km 银行"，结果为空 → 页面提示"该区域覆盖不足" → 用户点击"请求补充" → 生成反馈 + 定向抓取任务（scope=该坐标 1km）→ 抓取执行 → 新增 POI 入库 → 用户再次查询可见 → 反馈标记"已解决"。

**链路 C：热点闭环（查询 → 调度）**
`query_log` 持续写入 → 每日聚合出热点网格 → 调度器次日优先抓取热点区域（频率 ×2）、冷区降低（频率 ÷2）→ 数据新鲜度提升 → 查询体验改善 → 更多查询。

> 三条链路必须能在一个演示脚本里连续跑通（见 11.3）。

### 6.3 闭环度量指标

| 指标 | 定义 | 目标值 |
| --- | --- | --- |
| 数据新鲜度 | `now - last_fetched_at` 的中位数 | ≤ 7 天 |
| 反馈闭环时长 | 反馈创建到状态终结的平均耗时 | ≤ 24 小时（P90） |
| 反馈采纳率 | 采纳数 / 已处理数 | 作为质量参考，不设硬指标 |
| 热点覆盖率 | 热点区域中"7 天内更新过"的占比 | ≥ 80% |
| 查询驱动占比 | 由反馈/热点触发的抓取任务 / 总任务数 | ≥ 30%（体现"查询驱动运营"） |

- 前端单测 + E2E 通过；构建无警告级错误。
- 代码评审通过；无 P0 级缺陷。

### 11.3 演示脚本（10 分钟，必须一次跑通）
1. 打开地图，看到某区域银行与小区分布（FR-Q-01）。

6. 对一片空白区域提交"请求补充" → 生成定向抓取任务（FR-F-05）→ 执行完成 → 地图出现新点位（链路 B）。
7. 打开运营看板：任务成功率、热点区域、反馈积压（FR-O-03）。
