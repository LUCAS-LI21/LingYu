## 背景

用户在办理金融业务、选择居住地等场景下，需要全面了解周边银行网点和小区的详细信息。然而，这些数据分散在地图服务、房产网站、银行官网等多个渠道，且查询方式单一，难以进行综合分析和决策。本赛题要求设计并实现一个系统，能够自动抓取银行、小区等 POI（兴趣点）信息，并提供地图式、列表式等多种查询方式，形成数据持续更新与用户交互的业务闭环。

## 功能需求

### 一、数据抓取与更新（数据抓取不能违法）

1. 从公开的地图服务（如高德、百度地图 API）、房产信息网站、银行官网等渠道抓取
   银行网点（名称、地址、经纬度、营业时间、服务类型、联系电话等）
   和小区（名称、地址、经纬度、建成年代、均价、物业费、周边配套等）信息。
2. 支持定时自动抓取与手动触发抓取，具备增量更新与去重能力。
3. 提供数据清洗功能，处理缺失值、格式不一致等问题。

### 二、数据存储与管理

1. 结构化存储抓取的数据，设计合理的数据库表结构（如银行表、小区表、地理位置表等）。
2. 支持数据版本管理，记录每次更新的时间与来源。

### 三、多维度查询与展示

1. **地图式查询**：在电子地图上标注银行和小区的位置，支持缩放、平移。用户可通过框选、点击等操作查看详细信息弹窗。支持图层切换（仅显示银行、仅显示小区或同时显示）。
2. **列表式查询**：以表格或卡片列表展示搜索结果，支持按区域、银行类型、小区价格范围、建成年代等条件筛选，支持排序和分页。
3. **组合关联查询**：支持查询特定小区周边的银行网点（如距离某小区 1 公里内的所有 ATM），或查询某银行服务范围内的小区信息。
4. 查询结果可展示统计图表（如某区域银行密度图、小区价格分布等）。

### 四、用户交互与反馈

1. 允许用户对数据进行纠错、补充（如某银行已关闭、小区信息有误），提交后进入审核队列或直接更新（根据设计）。
2. 记录用户查询行为，用于优化抓取策略（如热门查询区域优先更新数据）。

### 五、业务闭环要求（核心）

系统必须形成"数据抓取 → 清洗存储 → 多维度查询展示 → 用户反馈/纠错 → 触发重新抓取或更新"的完整闭环。例如：

- 用户通过地图发现某小区周边缺少银行网点，提交"新增银行"请求，系统可自动触发该区域的重新抓取或通知管理员核实；
- 系统根据用户查询热点，动态调整抓取频率和区域，确保数据时效性；
- 用户反馈的数据错误经审核后，立即更新至数据库，并同步反映在地图和列表展示中。

不允许只做静态的数据抓取与展示，必须体现数据持续更新、用户参与优化和查询驱动的数据运营闭环。

## 非功能需求

1. 系统架构清晰，模块化设计，便于扩展新的数据源或查询方式。
2. 前端界面友好，地图交互流畅，列表加载快速。
3. 数据抓取需遵守目标网站的 robots 协议及相关法律法规，避免高频请求影响目标服务。
4. **必须提供独立部署方案（Docker 镜像/脚本），确保可在指定服务器运行。**
