# 1 需求理解

赛题要求做一套"能自己找数据、能持续更新、能让用户参与"的 POI 系统，而不是一张静态的银行/小区地图。我们把需求拆成三层：**数据层**要解决"从哪来、能不能存"——地图开放平台的接口协议明确禁止存储，房产网站多数 robots 全站禁止，所以必须把数据源按"可入库 / 仅展示 / 禁用"分级，主库只放 OSM、银行官网、政府开放数据这类许可清晰的来源；**查询层**要解决"查得到、查得准"——地图、列表、统计三种形态之外，真正有业务价值的是关联查询（小区周边 1 公里有哪些 ATM、某网点服务半径内覆盖哪些小区），这要求坐标与距离计算可靠；**运营层**要解决"数据会旧"——用户反馈和查询热点必须能反过来驱动采集，否则系统上线即过期。

因此我们定义的闭环是：采集 → 清洗入库 → 查询展示 → 用户反馈 → 审核生效 → 再采集。其中最关键的不是链路存在，而是**每一跳都可演示、可追溯**：反馈由谁在什么时候改了哪个字段要能查到（版本表 + 字段级来源），抓取任务为什么失败要能看到错误摘要，热点为什么优先更新这个区域要能按公式复算。这也是我们后续所有设计取舍的出发点。

| 2    | 定时自动抓取     | 每 30 分钟一轮，按热点优先级选择抓取区域                                            |

# 3 新增功能

表 2 需求之外新增的功能

| 序号 | 功能项                 | 功能描述                                                                   | 为何新增                                                                 |
| ---- | ---------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1    | 三级授权模型           | 数据源分 L1 可入库、L2 仅展示、L3 禁用，落在 `ds_source.storage_policy`    | 高德协议第 3.5 条禁止存储 API 返回数据，不区分就无法合法建库             |
| 2    | 字段级来源溯源         | `poi_field_source` 按 `(poi_type, poi_id, field)` 记录最后写入者与来源 URL | 一行数据常被 OSM、政府库、用户先后补全，行级 `source` 说不清字段归属     |
| 3    | 众包补坐标             | 用户在地图上为缺坐标小区标点，审核通过后转正                               | 4,940 个小区只有名称地址，公开数据里没有小区级坐标，商业地图坐标禁止落库 |
| 4    | AI 信息抽取            | 搜索 → 抽取 → 复核 → 规则校验，只产出建议，人工采纳才写库                  | 官网营业时间等字段非结构化，纯规则覆盖率低；但必须防模型编造             |
| 5    | 热点优先级公式         | `priority = 查询次数 + 2 × 零结果次数`，可 SQL 复算                        | 调度需要一个可解释、可复算的排序依据，而不是拍脑袋                       |
| 6    | 离线降级               | 后端不可达时前端回落内置种子数据并提示                                     | 演示环境网络与代理不可控，不能因为一次断网就白屏                         |
| 7    | ATM 专项采集与互斥展示 | 单独采集 ATM（368 台），地图同一时间只显示网点或 ATM                       | 两类点位坐标重叠严重，同屏叠加会糊成一片                                 |
| 8    | 小程序端复用同一后端 | 12 个页面（地图/列表/洞察/详情/反馈/后台等）与 Web 同仓，共用响应信封、坐标系与鉴权 | 同一后端要同时服务 Web 与小程序端，契约先行的成本最低 |

# 4 核心流程

## 4.1 业务闭环流程

![图 1 业务闭环：五步主干 + 三条可演示链路](assets/fig2-loop.png)

流程以"采集 → 清洗入库 → 查询展示 → 用户反馈 → 审核生效"为主干，审核结果既写回主表，又作为下一轮采集的输入。主干下沉三条链路：A 纠错闭环处理"数据不对"，用户提交后按字段风险分流，低风险自动采纳，采纳即写版本并改主表，前台立即可见；B 补采闭环处理"这里没数据"，审核通过新增点位后先落暂存表，再围绕锚点建定向任务；C 热点闭环处理"先更新哪里"，查询写日志、按天聚合热点、调度器按优先级取区域。三条链路共用同一套表与接口，可在一次演示里连续跑通。

## 4.2 数据采集与入库流程

![图 2 五条采集入口共用一条清洗与入库链路](assets/fig4-collect.png)

采集侧有五个入口：定时任务、手动触发、反馈定向、批量导入、AI 抽取。五条入口进入同一条处理链路：先做合规校验（robots、白名单、存储策略），再抓取解析（多镜像轮换、UA 与限速），然后清洗归一（坐标转换、品牌与地址归一），最后幂等入库。入库时按主键 upsert，跨源重复用名称归一加 165 米球面距离判定。没有坐标的数据一律先入暂存表，等人工或众包标注后再转正，绝不伪造位置进主表。
