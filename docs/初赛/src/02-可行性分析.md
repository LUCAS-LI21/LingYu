# 1 结论

本方案在技术、数据、时间三个维度均具备落地条件，且已产出可复现的初步证据，不属于纸面设想。

**技术上可行**：所选前后端与数据库均为成熟组件，五条采集通道、三类查询、三条闭环全部有可运行代码；接口验收 32 项全部通过，独立部署的三容器环境已在本机跑通。

**数据上可行**：主数据来自 OSM（ODbL 可入库）、11 家银行官网、8 个深圳市开放数据集与金融监管总局持牌底册，全部属于可存储、可再加工的来源；已入库 5,104 个 POI，银行覆盖深圳持牌网点的 76.8%，小区均价、建成年份等商业属性也已找到合法来源并部分落地。

**时间上可行**：距 12 月 20 日尚有 31 天，功能已进入收尾期，剩余工作集中在数据补齐、部署加固与材料打磨，按 20% 缓冲排期仍有余量。

## 2.3 技术难点与解法

**（1）空间查询性能**。小区与网点总量万级，直接对全表算球面距离会随数据量线性劣化。解法是先按半径换算经纬度矩形走 `(lat, lng)` 索引预筛，再用 `ST_Distance_Sphere` 精算，实测 1 公里周边查询 9 毫秒返回 47 条。

**（2）坐标系混用**。OSM 是 WGS-84，银行官网多为 GCJ-02，平安银行是 BD-09，直接入库会偏 300～600 米。解法是入库前统一转 WGS-84（BD-09 → GCJ-02 → WGS-84 两级转换），出站跳转国内地图时再转回 GCJ-02，转换函数有单测锁死往返误差小于 2 米。

**（3）抓取源不稳定**。公共 Overpass 实例经常 502/504，Java 直连尤其明显。解法有三层：配置三个镜像端点轮换、银行与小区分两段抓取（小区失败只把任务标记为 `partial`，不整单失败）、抓取统一走本地代理；同时把"已入库数据"与"实时抓取"解耦，演示不依赖当场抓取成功。

**（4）合规边界**。高德服务协议 3.5 条禁止存储 API 返回数据，因此把数据源分为 L1 可入库、L2 仅展示、L3 禁用三级，L2 通道不写库、不缓存，页面标注来源；需要坐标又缺合法来源的 4,940 个小区，改走"用户/管理员在地图上标点"的自产数据路径。

**（5）AI 抽取的可信度**。模型可能编造地址，因此 Agent 只产出建议、不直接写库；建议必须附带能回到原始搜索结果的证据（URL 精确匹配 + 文本归一化包含），并经过规则校验（地址必须包含所属行政区），最后由管理员点采纳才落库，落库时写 `poi_version` 与字段级来源。

## 3.4 合规证据

赛题明确要求"数据抓取不能违法"。本项目对每个目标站点做过实测：链家、贝壳 `robots.txt` 为全站 `Disallow`，直接禁用；工商银行、建设银行 robots 返回 404（无声明），可低频访问；高德服务协议 3.5 条原文禁止存储，故只做实时展示。所有入库数据均有可存储许可，页面固定展示数据来源与免责声明。

## 4.2 关键路径与缓冲

关键路径为"众包标点 → 转正 → 地图可见"这一条：它依赖用户/管理员操作，不能靠程序自动完成。应对方式是把标点做成 30 秒一次的操作（地图上点一下即可），并在演示脚本里固定演示 3 个点位；即使标点量不达标，也不影响主线演示，只是覆盖率数字低一些。

时间缓冲约 6 天（占 19%），集中在最后一周，用于吸收抓取源波动、部署环境差异这类不可控因素。

## 4.3 资源与协作

项目采用"双会话并行"开发：后端会话负责 Spring Boot、数据库、采集脚本；前端会话负责 Vue 页面与交互；共享契约（`docs/api/openapi.yaml`）与目录所有权在协作文档中约定，避免互相覆盖。AI Agent 承担重复性工作（信息抽取、批量补字段），人工只做审核与决策。

# 6 结论

综合判断：**可行，且已过"能不能做"的阶段，进入"做得好不好"的阶段**。

技术侧没有未验证的关键路径，所有对外能力都有可运行代码与实测记录；数据侧主数据合法可得、覆盖率可量化，缺口有明确且已实现的补齐通道；时间侧 31 天排期留有约 19% 缓冲，且核心功能已可演示。最大不确定性来自公共数据源的稳定性，已用"多镜像 + 两段式 + 本地库兜底"把影响限制在"数据更新快慢"，而不是"系统能不能用"。
