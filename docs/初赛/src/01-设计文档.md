# 1 系统概述

## 1.1 建设目标

本系统面向"办金融业务、选居住地"两类真实决策场景：用户在办理开户、贷款、存取款时需要知道周边有哪些网点、几点开门、能不能办对私业务；在选择居住地时需要知道小区的位置、价格、建成年份，以及周边银行、ATM 的密度。这些信息目前分散在地图服务、银行官网、房产网站和政府部门的不同渠道里，且各渠道的字段口径、坐标系、更新节奏都不一致。

系统以深圳市 10 个行政区为范围，把可合法入库的银行网点与住宅小区 POI 汇聚到一处，提供地图式、列表式与组合关联三类查询，并用"用户反馈 + 查询热点"驱动数据持续更新，形成**采集 → 清洗入库 → 查询展示 → 用户反馈 → 审核生效 → 再采集**的业务闭环。截至 2026-11-19，已入库 POI 5,104 个（银行 1,528、小区 3,576），另有已取得名称与地址、但缺坐标的待定位小区 4,940 个，进入"众包标注—审核—转正"通道。

# 2 系统架构

## 2.1 总体架构

![图 1 系统总体架构（五层 + 三条横切能力）](assets/fig1-architecture.png)

系统采用**前后端分离 + 单库多表 + 统一视图**的分层结构，自上而下分为五层。数据源层按三级授权模型隔离：OSM、银行官网、政府开放数据属 L1 可入库，高德 API 属 L2 仅展示、代码层禁止写库，链家/贝壳等 L3 站点直接禁用。采集与接入层提供定时调度、手动触发、反馈定向任务、批量导入与 AI 抽取五条入口，统一走清洗与幂等去重。数据存储层用两张业务主表加一张 `UNION ALL` 视图承载查询，另设版本表、字段级来源表与四张闭环运行表。服务层以 Spring Boot 提供 REST 接口，鉴权、限流、空间查询与统计聚合在服务内完成。展示层为 Vue 单页应用，地图、列表、洞察、合规说明与运营后台共用同一套接口。

## 2.2 技术选型

表 2 技术选型与理由

| 层 | 选型 | 版本 | 选择理由 |
| --- | --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite | 3.5 / 5.9 / 8.3 | 组合式 API 便于拆分地图与列表逻辑；Vite 构建快，本地演示启动成本低 |
| 地图 | Leaflet + OSM 瓦片 | 1.9 | 免 Key、可离线兜底；避免商业地图 API 的存储与配额约束 |
| 样式 | Tailwind CSS | 4.3 | 原子类控制密度，地图与后台共用一套设计变量 |
| 后端 | Spring Boot + MyBatis-Plus | 3.2.5 / 3.5.5 | 定时任务、事务、JDBC 批量导入成熟；本地 Java 17 工具链齐备 |
| 数据库 | MySQL 8.0 | 8.0.45 | `ST_Distance_Sphere` 原生球面距离，省去空间扩展依赖 |

## 2.3 关键设计决策

（1）**物理分表 + 逻辑统一视图**。银行与小区字段差异大，物理分表避免大量空列；查询侧用视图 `v_poi` 合并，分页、排序、筛选只写一套 SQL，`status='closed'` 在视图层过滤，保证"关掉就查不到"。

（2）**三级授权模型落到表字段**。`ds_source.storage_policy` 取 `storable / display_only / forbidden`，采集侧按策略决定能否写库；高德只做实时展示通道，响应头 `Cache-Control: no-store`，不落库、不缓存。

（3）**版本 + 字段级来源双轨留痕**。`poi_version` 记录整行变更前后快照与操作人；`poi_field_source` 按 `(poi_type, poi_id, field)` 记录每个字段"最后由谁写入、来源 URL 是什么"，解决"同一行数据被多个来源先后补全"的溯源问题。

（4）**坐标双轨**。数据库统一存 WGS-84；对外返回时同时给出 `lng/lat`（算距离、配 OSM 底图）与 `gcjLng/gcjLat`（跳转高德、腾讯、微信地图），避免偏移 500 米。

（5）**热点优先级公式固定**。`priority = 查询次数 + 2 × 零结果次数`，零结果权重更高，因为"这里有查询但没有数据"是最强的补采信号；调度器只读聚合表，不实时扫日志。

# 3 业务闭环流程

## 3.1 闭环主干

![图 2 业务闭环流程（主干 + 三条链路）](assets/fig2-loop.png)

业务闭环以五步主干串起：数据采集、清洗入库、查询展示、用户反馈、审核与生效，审核结果既写回主表又作为下一轮采集的输入，形成闭环。围绕主干下沉三条可独立演示的链路：**A 纠错闭环**解决"数据不对"，**B 补采闭环**解决"这里没有数据"，**C 热点闭环**解决"哪里该优先更新"。三条链路共用同一套表与接口，只是触发源与处理分支不同——反馈改变数据，查询改变调度，采集再回填缺口。

## 3.2 三条闭环

表 3 三条闭环的触发、处理与可见结果

| 链路 | 触发 | 处理 | 可见结果 |
| --- | --- | --- | --- |
| A 纠错 | 用户在地图/列表/详情提交反馈 | 低风险字段（电话、营业时间、均价、物业费、建成年份）自动采纳；关闭、改名、改坐标、新增点位转人工审核 | 采纳后同一事务写 `poi_version` 并改主表，接口立即返回新值；关闭点位从视图消失 |
| B 补采 | 审核通过"新增点位"类反馈 | 先落 `bank_pending` / `community_pending` 暂存，再以锚点为中心 ±0.012°（约 1.3 公里）建定向抓取任务 | 抓取完成后新点位入库、地图可见；抓不到的留在待定位名录，等人工或众包标坐标 |
| C 热点 | 每次列表/周边查询 | 写 `query_log`（区域、网格、结果数、耗时）；每日 02:30 或手动重算 `hot_region` | 定时任务按优先级选网格抓取，缺口区域数据变新，查询结果变全 |

## 3.3 闭环度量

表 4 闭环度量指标

| 指标 | 定义 | 当前值 | 目标值 |
| --- | --- | --- | --- |
| 反馈闭环时延 | 提交到版本落库的时间差 | < 1 秒（同秒落库，已实测） | ≤ 5 秒 |
| 反馈触发补采 | `trigger_type='feedback'` 的任务数 | 6 | 持续增长 |
| 字段级溯源覆盖 | 有来源记录的字段数 | 9,561 | 全字段 |

| 银行覆盖率 | 入库网点 / 深圳持牌网点（1,989） | 76.8% | ≥ 85% |

# 4 核心接口定义

## 4.1 通用约定

- **响应信封**：所有接口返回 `{code, message, data}`，`code=0` 表示成功；业务错误另用 HTTP 状态码表达（400 参数错、401 未登录、404 不存在、409 状态冲突、429 限流、405 方法错）。
- **鉴权**：`/api/v1/admin/**` 需 `Authorization: Bearer <token>`，token 为 HMAC-SHA256 签名，默认有效期 12 小时；审核人取自 token 主体，不信任请求体。
- **坐标系**：请求与存储统一 WGS-84；`gcjLng/gcjLat` 为服务端换算的国测局坐标，仅供跳转国内地图。
- **限流**：匿名写接口（反馈、坐标提交）按 10～20 次/分钟限流，超出返回 429。

## 4.3 关键接口详述

### 4.3.1 GET /api/v1/pois

请求参数：`types`（bank,community）、`district`、`keyword`、`branchType`（all/branch/atm）、`minPrice`、`maxPrice`、`minYear`、`maxYear`、`west`/`south`/`east`/`north`（bbox）、`sort`（default/name/priceAsc/priceDesc/yearDesc/yearAsc）、`page`、`size`（≤20,000）。响应示例：

```json
{"code":0,"message":"ok","data":{
  "items":[{"id":"osm-node-4866753941","type":"bank","name":"Bank of China",
            "district":"宝安区","lng":113.841718,"lat":22.604593,
            "gcjLng":113.846699,"gcjLat":22.601611,"brand":"中国银行",
            "branchType":"atm","source":"OpenStreetMap","license":"ODbL","sourceLevel":"L1"}],
  "total":5104,"page":1,"size":20}}
```

### 4.3.2 GET /api/v1/pois/nearby

请求参数：`lng`、`lat`（必填，WGS-84）、`radius`（米，默认 1000，上限 5000）、`branchType`、`limit`（≤200）。实现上先用半径换算的经纬度矩形走 `(lat, lng)` 索引预筛，再用 `ST_Distance_Sphere` 精算，避免全表计算球面距离。响应按距离升序：

```json
{"code":0,"data":{"items":[
  {"poi":{"id":"import-249265493","name":"招商银行深圳时代广场支行",
          "address":"深圳市福田中心区益田路4068号卓越时代广场一楼",
          "lng":114.058673,"lat":22.542872,"source":"招商银行官网"},
   "distance":83.34}],"total":47}}
```

### 4.3.3 POST /api/v1/feedback

请求体：`poiType`、`poiId`、`poiName`、`type`（error/closed/add）、`field`、`newValue`、`description`、`contact`。返回受理编号与初始状态；低风险字段在服务端开关允许时自动采纳，默认关闭以保证匿名请求不能直接改主表。

```json
{"code":0,"data":{"code":"FB20261119-0103","status":"pending"}}
```

### 4.3.4 POST /api/v1/admin/feedback/{code}/approve

采纳时按反馈类型分流：普通纠错写主表并记版本；`add` 类型不直接改主表，而是落暂存表并以锚点建定向抓取任务，返回任务号与锚点坐标。同一反馈重复采纳返回 409，避免重复写版本。

```json
{"code":0,"data":{"code":"FB20261119-0099","status":"need_refetch","applied":[],
  "anchorLng":114.052335,"anchorLat":22.649201,
  "pendingStaged":true,"pendingKind":"bank","jobId":440}}
```

## 5.4 索引与约束

- 空间查询：`poi_bank`、`poi_community` 各建 `(lat, lng)` 复合索引，框选与半径预筛都走索引。
- 去重：`poi_bank`、`poi_community` 以来源标识为主键；跨源重复用"名称归一 + 165 米球面距离"判定，删除项写入 `dedupe_log` 作为抓取黑名单。
- 幂等：抓取按主键 upsert，重复执行两次记录总数不增加。
- 唯一性：`feedback.code`、`ds_source.code`、`sys_user.username`、`hot_region(grid, stat_date)` 均建唯一索引。
- 迁移：`db/migration/V1–V3` 由 `SchemaMigrator` 按版本顺序执行，`schema_version` 记账。

# 6 约束与后续

**已知限制**：（1）`v_poi` 为 `UNION ALL` 视图，全量拉取（5,000 条）P95 约 1 秒，后续将拆为按类型查询或物理汇总表；（2）公共 Overpass 实例不稳定，抓取任务有效产出率 64.2%，靠多镜像轮换与两段式抓取兜底；（3）尚未引入 Flyway，结构变更依赖版本化 SQL 脚本；（4）未启用 TLS 与角色分权，仅满足内网演示；（5）小区均价、建成年份等字段仍有 2,512 条演示值，已与真实值分列存储并在前端标注。

**后续演进**：接入小程序端复用同一套接口（契约已定稿）；补齐抓取任务回写反馈状态；按数据源维度做质量看板（缺失率、重复率、新鲜度）。
