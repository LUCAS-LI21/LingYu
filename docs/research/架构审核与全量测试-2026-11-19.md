# 架构审核 + 全量测试（2026-11-19）

五路子代理从**分层/数据/契约/运行时/业务闭环**五个维度做了全局评审，本轮同时修掉了其中 12 项，
并在**开发栈 + Docker 栈 + 全新库**三套环境下跑了完整测试矩阵。

## 一、架构审核结论（按维度）

### 1. 分层与模块边界

| #   | 结论                                                                                           | 严重度 | 状态    |
| --- | ---------------------------------------------------------------------------------------------- | ------ | ------- |
| 1.1 | 没有 repository 层：service 直连 JdbcTemplate，controller 也写 SQL（PoiController:28/171-211） | 严重   | 🔴 待解 |
| 1.2 | 业务编排堆在 controller（AdminController 注入 6 个依赖，串起"审核→暂存→抓取"）                 | 严重   | 🔴 待解 |
| 1.3 | 前端双传输层：axios（lib/http.ts）+ fetch（api/server.ts），token 两种存法                     | 严重   | 🔴 待解 |
| 1.4 | `api/pois.ts` 690 行兼做传输/离线兜底/演示数据/过滤/分页                                       | 严重   | 🔴 待解 |
| 1.5 | poi↔admin、feedback↔admin 存在包级循环依赖                                                     | 中等   | 🔴 待解 |
| 1.6 | 球面距离、品牌推导、表名白名单、toJson 各有 2–4 份实现                                         | 中等   | 🔴 待解 |
| 1.7 | `ds_source` 是"空注册表"：建了表却没有代码读取，加数据源仍要改 IngestService + 写新脚本        | 严重   | 🔴 待解 |

**总评**：分层只到包名，真实集成边界是数据库。扩数据源撑得住（管线短、L1/L2 已隔离），
扩端（小程序）风险偏高——接口是无类型 Map、`/meta` 手抄。

## 三、上生产前必须处理的 5 件事（评审共识）

1. **数据层重构**：`v_poi` 换物理汇总表或按类型拆查询；`avg_price` 真假分离；引入 Flyway 单一真相。
2. **可观测性**：actuator + metrics + request-id + nginx 访问日志（含耗时/XFF）+ 日志轮转。
3. **安全收口**：TLS、`AUTH_SECRET` 显式随机、清除弱默认口令、独立最小权限 DB 账号、角色分权。
4. **闭环补全**：抓取任务回写反馈状态、`need_refetch` 出口（已修）、用户状态查询（已修）、热点上前台。
5. **交付工程化**：镜像按 digest 固定、后端进 CI、资源限额、`depends_on` 解耦、备份与恢复演练。

## 五、结论

- **功能与数据**：可演示、可信（真实价格/租金/建成年份/建设单位均有来源），三套环境行为一致。
- **架构**：**分层只到包名**，集成边界是共享数据库；扩数据源代价可控，扩端（小程序）前需先补 DTO 与单一 HTTP client。
- **工程**：测试矩阵齐（32 接口 + 20 e2e + 15 冒烟 + 负载 + 失败模式），但**可观测性、迁移、TLS、角色**仍是空白。

一句话：**演示级已达标，生产级差 5 件事**（见第三节）。
